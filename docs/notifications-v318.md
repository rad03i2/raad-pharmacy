# إشعارات دفتر صيدلية رعد — 3.3.18 (versionCode 52)

## السبب المثبت

دالة `send-financial-notification` كانت تستعلم عضوية المستخدمين من `profiles`
باستخدام `service_role` دون صلاحية SELECT. قاعدة الإنتاج أعادت
`has_table_privilege(..., 'SELECT') = false`، و12 حدثاً احتفظت بخطأ
`recipient_membership_lookup_failed`، بينها 10 أحداث يديرها الخادم.
وكان جدول `notification_deliveries` خالياً. نتيجة استدعاءات pg_net كانت HTTP 503.
لذلك عملت تنبيهات Realtime أحياناً، بينما لم يصل مسار الإرسال إلى FCM.

يوجد الآن 3 مديرين و6 سجلات token فعالة موزعة على 3 مستخدمين. سجلان فقط
يحملان بيانات إصدار حديثة (50 و51)؛ الأربعة الأخرى تحمل الإصدار 0 وخصوصية مفعلة.
عدد السجلات لا يثبت وجود 6 هواتف فعلية؛ FCM يحدد الرموز المنتهية عند الإرسال.

## التعديل

- منح الخدمة قراءة أربعة حقول عضوية فقط: id، pharmacy_id، role، is_hidden.
  اختبار SQL تحت دور الخدمة نفسه أصبح يعيد المديرين الثلاثة.
- استمرار الحدث الدائم، مشغل قاعدة البيانات، وCron. إرسال العملية يعتمد على
  الخادم بعد المزامنة؛ WorkManager في هاتف المرسل مسار إضافي.
- 3.3.18 يرسل FCM عالي الأولوية برسالة data مستقلة لكل حدث، دون collapse key.
  يعرض الهاتف التفاصيل من اللقطة الخادمية فوراً ثم يرسل إقراراً مستقلاً بعد العرض.
- إذا قُبلت الرسالة ولم يصل إقرار عرض بعد 60 ثانية على الأقل، يستخدم الخادم
  تنبيه Android تلقائياً واحداً احتياطياً. توقيته الفعلي يتأثر بدورة Cron وإعادة المحاولة.
  هذا انتظار في مسار الاسترداد فقط؛ الإرسال المباشر بلا مهلة مصطنعة.
- قبول FCM وتوثيق العرض حقول منفصلة. لا يُعاد إرسال تنبيه احتياطي قُبل بالفعل.
  مفاتيح event/device وبصمة token تمنع التكرار غير المنضبط وتسمح بتغير الرمز.
- Realtime يعرض الشريط الداخلي، ويترك الإشعار الخارجي للمسار الخادمي على الجهاز
  المسجل بالإصدار الجديد. الإشعارات المحلية والتلقائية تستخدم الوسم نفسه لكل حدث.
- إزالة انتظار الشبكة من قفل العرض؛ FCM لا ينتظر جلب جلسة أو تفاصيل من الخادم.
  التفاصيل تشمل المنفذ والزبون والمبلغ والرصيد الموثق. لا يعاد حساب رصيد ناقص.
- تثبيت معرف الجهاز ومعرف تسجيل token بين الاستدعاءات المتزامنة. تسجيل token
  مستقل عن قفل المزامنة المالية، وتغيير الخصوصية يضيف مهمة تحديث بدلاً من إسقاطها.
- خصوصية الجهاز تُحترم في البيانات والمحتوى المرئي، مع قناة صوت الآيفون الحالية.
  البيانات المرسلة بوضع الإخفاء تبقى مخفية محلياً حتى لو تغير الإعداد أثناء الطريق.
- عند إبلاغ FCM عن حذف طابور الرسائل، يسترجع WorkManager الأحداث الدائمة، مع
  حفظ عدم التكرار وعدم تقدم مؤشر الاسترداد إذا فشل العرض.
- أوقفت إعادة إرسال 30 تنبيهاً تاريخياً فاشلاً. احتُفظ بالأخطاء وحالة عدم التسليم؛
  لم تُعلّم بأنها وصلت ولم تُحذف أحداثها أو العمليات المالية.

خدمة التشغيل المستمر وصوت نجاح العملية وقاعدة البيانات والتصميم وهوية منشئ الحركة
لم تتغير. ترقية SQL إضافية في `supabase/push-v318.sql`، والدالة المنشورة إصدار 17.

## الأدلة والاختبارات

- 14 اختبار Deno و3 اختبارات Node نجحت محلياً.
- استدعاء الخادم الحقيقي (pg_net رقم 26) لاختبار FCM بـ`validate_only` أعاد HTTP 200،
  مع `ok: true` و3 مديرين. الحالات الثماني للإصدارات القديمة والجديدة، وخصوصية التفاصيل،
  والمسار الأساسي والاحتياطي، أعادت جميعها HTTP 200 من FCM. لم تُرسل تنبيهات تجريبية.
- اختبارات Android المضافة تغطي التفاصيل والإخفاء والنسخة العامة لشاشة القفل وتعدد
  الأحداث ومنع التكرار ودوران token واختيار مسار العرض بعد نجاح التسجيل.
- CI يفحص Kotlin/Room/Compose وLint Release والبناء وتوقيع APK واستمرارية شهادة
  الإنتاج وزيادة versionCode. نشر APK مشروط بهذه الفحوص وباختبارات الخادم.

## اختبار ميداني مطلوب على الهواتف الثلاثة

ثبّت النسخة كتحديث وافتحها مرة على كل هاتف لتحديث تسجيله، ثم سجل لكل تجربة:
معرف الحدث، وقت وصول العملية للخادم، قبول FCM، ظهور التنبيه، الفرق بالثواني، وعدد التنبيهات.
لا تنشئ ديوناً وهمية في البيانات الحقيقية؛ استخدم عمليات حقيقية مصرحاً بها أو حساب اختبار منفصل.

| التجربة | النتيجة المطلوبة |
|---|---|
| رعد يسجل ديناً، أحمد وفؤاد بالخلفية | إشعار واحد لكل جهاز مع التفاصيل خلال ثوانٍ عادةً |
| أحمد يسجل تحصيلاً | اسم أحمد والمبلغ والرصيد الصحيحان عند الجهازين الآخرين |
| قفل الشاشة أو تصفح تطبيق آخر | ظهور التنبيه وفق إذن الإشعارات وإعداد شاشة القفل |
| انقطاع الإنترنت ثم 3 عمليات وعودته دون فتح التطبيق | استعادة الأحداث الثلاثة، بلا تكرار للعملية الواحدة |
| خمس عمليات متتابعة | خمس هويات أحداث مستقلة ولا تضيع الأرصدة |
| إخفاء المبالغ | لا أسماء زبائن ولا مبالغ في التنبيه أو البيانات المرسلة للجهاز بعد تحديث الخصوصية |
| تعديل حركة من مستخدم آخر ثم حذفها | المنفذ الصحيح مع بقاء منشئ الحركة الأصلي |
| إزالة التطبيق من قائمة التطبيقات الحديثة | استمرار الخدمة واستقبال FCM حيث يسمح النظام |
| توفير الطاقة/Doze ثم الخروج منه | متابعة الاسترداد، مع تسجيل التأخير الحقيقي |
| تحديث نسخة قديمة وتغير token | تسجيل الإصدار 52 والرمز الجديد دون تغيير شهادة التطبيق |

## حدود القياس والضمان

لا تتوفر هواتف فعلية في بيئة التنفيذ؛ لا يوجد ادعاء باختبار ميداني أو وصول مضمون 100%.
قبول FCM ليس دليلاً على أن المستخدم شاهد التنبيه. إقرار الجهاز يعني نجاح العرض المحلي
أو ملاحظة تنبيه نشط/فتحه، وقد يصل إلى الخادم لاحقاً بسبب الإنترنت.

الرسائل التلقائية الاحتياطية قابلة للدمج أثناء انقطاع الإنترنت؛ المسار الأساسي المستقل
واسترداد سجل الخادم هما ما يحمي تعدد الأحداث. إيقاف التطبيق إجبارياً أو قيود TECNO
أو عدم الإزعاج/الصامت/رفض الإذن قد يمنع أو يؤخر العرض. لا يتم تجاوز خيارات الهاتف.
قد توجد إعادة تنبيه في سباق نادر بين إقرار متأخر وتنبيه احتياطي بدأ إرساله؛ الوسم الثابت
يحافظ على عنصر واحد للعملية نفسها في لوحة الإشعارات.

تغيير الإخفاء دون إنترنت يطبق محلياً فوراً، لكن خصوصية التنبيه التلقائي تُحدَّث بعد
وصول إعداد الجهاز للخادم. هذا حد في مسار Android التلقائي، ويجب اختباره خصوصاً بعد تغيير الإعداد.

## التراجع

احتفظ بنسخة الدالة السابقة (15) قبل النشر. التراجع يتطلب إعادة نشر الدالة السابقة
واستعادة تعريف `raad_private.dispatch_push` إذا لزم. الأعمدة الإضافية تبقى للتوافق؛
لا تمسح قواعد البيانات أو الأرصدة، ولا ترفع التنبيه التاريخي الموقوف جماعياً.
لا تُسحب صلاحية العضوية قبل استعادة مسار إرسال لا يحتاج ذلك الاستعلام.
