# تقرير المراسلات والتنبيهات — 3.3.22.11 (79)

## التشخيص والأدلة

- المرجع قبل التعديل: `6762d267f4c345f107613e187ef54ac81b55c014`، وآخر إصدار رسمي `3.3.22.10` (78).
- مقارنة `v3.3.22` بالإصدار 78: تغيّر تخصيص هوية الجهاز لكل حساب في 3.3.22.8. لكن دوال الإرسال بقيت تستخدم `deviceId()` مباشرةً، دون تسجيل هذه الهوية قبل RPC. التحقق في الخادم يرفض الجهاز غير المسجل برمز `MESSAGE_DEVICE_INVALID` أو `ALERT_DEVICE_INVALID`. أُعيد إنتاج هذا الرفض في اختبار معزول ثم نجح الإرسال بعد تسجيل الجهاز.
- كانت الواجهة تعرض «تحقق من الإنترنت» لمعظم الاستثناءات، بما فيها رفض الجهاز والصلاحيات. لا تحتوي السجلات المتاحة على محاولة المستخدم الفاشلة نفسها؛ لذلك لا يُنسب ذلك الحادث إلى رمز محدد دون سجل من الهاتف.
- كان بدء Realtime يأتي بعد المزامنة المالية وإعادة محاولات دفع الإشعارات. `subscribe()` لا ينتظر الاشتراك افتراضيًا، وعَلَم التشغيل لا يراقب فشل اشتراك التنبيهات أو انقطاعه. ظلت شاشة الحساب تعتمد على استعلام كل 10 ثوانٍ، وخدمة المتابعة على استدراك كل 30 ثانية.
- كان FCM يحدّث صندوق الرسائل ويعلّم الإشعار بأنه معروض، دون بث تنبيه الواجهة؛ وقد يمنع ذلك مسار Realtime اللاحق من بثه. فُصل منع تكرار التنبيه الداخلي عن إيصال عرض إشعار النظام.
- قاعدة البيانات: جدول `notification_events` ضمن publication، وسياسات القراءة تقيد الصيدلية والمستلم/المرسل. دوال RPC تقيد الجهاز والمستلم ومعدل الإرسال وتدعم UUID ثابتًا. لم تُفتح RLS أو تُعدّل بيانات مالية.
- الرموز النشطة وقت الفحص كانت للبناءات 60 و67 و68، ولم يظهر تسجيل دفع للبناء 78. هذا يثبت غياب التسجيل في تلك اللقطة، ولا يثبت وحده سبب غيابه على الهاتف.

## مسار التنفيذ بعد الإصلاح

زر الإرسال → تهيئة جلسة الحساب → تسجيل جهاز الحساب مستقلاً عن الدفتر وFCM → RPC بالمعرّف الثابت → التحقق من UUID المُعاد → عند ضياع الاستجابة، مطابقة الحدث المحفوظ بالمعرّف والمرسل والمستلم والنوع والمحتوى → طلب دفع دائم وفوري.

الاستقبال: اشتراك على مستوى التطبيق قبل المهام الطويلة → مراقبة تأكيد الاشتراك والانقطاع → استدراك بعد كل اتصال → دمج الرسائل بالمعرّف وتحديث الشارة → تنبيه داخلي مرة واحدة. مسار FCM يبقى قادرًا على العرض من البيانات المحلية دون انتظار جلسة الشبكة.

تُجدَّد الجلسة عبر إعداد Postgrest القائم، مع محاولة تجديد واحدة عند HTTP 401 وإعادة الطلب بالـUUID نفسه. يُمنع تأكيد الإرسال إذا تغيّر الحساب أثناء الطلب. حالات قبول FCM وعرض Android وقراءة الرسالة تبقى منفصلة عن تأكيد حفظ الحدث.

## التحقق

- نجحت اختبارات Node الثلاثة لحمولة إشعار التطبيق المغلق، و20 اختبارًا لوحدة النسخ الاحتياطي محليًا.
- نجح اختبار SQL بمعاملة فرعية تُلغى بالكامل: صيدليتان وثلاث هويات اصطناعية؛ رفض جهاز غير مسجل، ثم إرسال ورد وتنبيهان بالاتجاهين؛ عدم التكرار؛ حد المعدل؛ عزل الصيدلية؛ قصر القراءة على المستلم. أُثبت اختفاء الهويات والأحداث بعد rollback. لم تُستخدم حسابات المستخدمين الفعلية ولم يُرسل FCM اختباري.
- اختبارات Android الجديدة: ضياع استجابة بعد الحفظ، إيصال خاطئ، فشل التحقق، المهلة، الإلغاء، إعادة المحاولة بنفس UUID، تصنيف الأخطاء، دورة فصل/إعادة اشتراك، وتحديث الشارة والتنبيه الداخلي مرة واحدة عبر FCM المكرر.
- مرجع سجلات ما قبل الإصلاح: قبول FCM الأول لتنبيه بعد نحو 1.713 ثانية من إنشائه، ولرسالة بعد نحو 0.760 ثانية. هذه أزمنة قبول الخدمة وليست أزمنة وصول الهاتف أو عرض الواجهة.
- نتائج Android وRoom وCompose وlintRelease والبناء وشهادة التوقيع: تُراجع في فحوص PR ومسار النشر الرسمي المرتبطين بالإصدار؛ لا يُنشر APK قبل نجاحها.
- لا تتوفر هواتف فعلية في بيئة التنفيذ. زمن استقبال الواجهة المستهدف 1–2 ثانية لم يُقَس على هاتفين، ولم تُختبر Doze أو تبدلات الشبكة الفعلية أو توافق جهاز قديم مع الجديد ميدانيًا.

## التوافق والاختبار الميداني

لم تتغير هوية التطبيق أو بيانات الحسابات أو مخطط الدفتر أو المشاركة اليدوية عبر واتساب. لا حاجة لترحيل قاعدة بيانات أو نشر Edge Function لهذا الإصلاح. يبقى توقيع الإنتاج خاضعًا للمقارنة الإلزامية بشهادة الإصدار السابق في النشر.

1. حدّث التطبيق فوق النسخة المثبتة دون إزالته. افتح حسابين مختلفين على هاتفين واسمح بالإشعارات.
2. أبقِ شاشة الإعدادات مفتوحة لدى المستلم؛ أرسل رسالة ثم ردًا وتنبيهًا بكل اتجاه. راقب الشارة والتنبيه دون مغادرة الشاشة، وقِس من الضغط إلى ظهور الرسالة.
3. ضع أحد التطبيقين في الخلفية ثم أغلقه من قائمة التطبيقات وأعد الإرسال؛ لا تستخدم «فرض الإيقاف»، لأن Android يوقف الإشعارات للتطبيق المفروض إيقافه حتى فتحه.
4. افصل شبكة المستلم، أرسل حدثًا، وأعد الشبكة. تحقق من استدراكه وظهوره مرة واحدة. جرّب أيضًا بعد بقاء الجلسة فترة طويلة والتنقل بين الصفحات.
5. كرر بجهاز قديم `3.3.22` وآخر جديد. لا تُعد تجربة الهاتف ناجحة قبل تنفيذ هذه الخطوات فعليًا.
