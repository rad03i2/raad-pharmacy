# مقارنة الاتصال والمزامنة مع 3.3.22.4 — 3.3.22.15 (83)

## البلاغ والدليل المتاح

المستخدم أكد أن القديمة كانت تعمل على الهاتف نفسه وبالشبكة نفسها قبل تثبيت الجديدة. الصور توثق فشل الدخول، بقاء عملية محلية بانتظار الرفع، وانتظار إرسال رسالة. الصورة لا تتضمن الاستثناء التقني، لذلك لا يصح الجزم بأن السبب DNS أو TLS أو كلمات المرور أو الخادم.

في نافذة 2026-10-17 00:25–00:45 بتوقيت بغداد ظهرت في سجلات الخادم محاولات دخول وعمليات مالية ناجحة من أجهزة أخرى؛ كانت تسجيلات FCM المتاحة codes 60/67/68. لا تثبت هذه النجاحات وصول طلب الهاتف المتعطل. لم تُرسل أي عملية أو رسالة تجريبية إلى حسابات الصيدلية.

المقارنة مع tag v3.3.22.4 أثبتت تطابق عنوان Supabase والمفتاح العام ومكتبات Supabase 3.8.0 وKtor CIO 3.5.1 ومعرّف الحزمة وحقول العمليات المالية. لذلك لم يتم تبديل المشروع أو كلمات المرور أو محرك الاتصال بناء على التخمين. الإصدار 15/code83 يتجاوز رقم14 الذي ذكره المستخدم، بينما آخر tag منشور وقت بدء العمل كان13/code81.

## التحقق المطلوب والمنفذ

اختبارات HTTP تستخدم createCloudClient نفسه المستخدم في الإنتاج، محرك CIO الفعلي، sockets فعلية وخادم localhost مستقل. تشمل دخول عميلين، تبادل عملية وتعديلها بالمعرّف نفسه، فقد رد الخادم ثم إعادة المعرف دون تكرار، انتهاء مهلة ثم نجاح دخول ورفع لاحقين، استعادة الجلسة عبر SDK، وتصنيف رفض بيانات الدخول الفعلي. هذه اختبارات بروتوكول محلية وليست إثباتًا على وصول شبكة هاتف المستخدم.

اختبارات الإلغاء تغطي بقاء المراقب بعد مهلة طلب، توقفه عند إلغاء الأب، وعدم تحويل إيقاف العامل إلى نجاح أو retry، وإكمال دفعة صحية تستغرق40 ثانية داخل قفل الدفتر الفعلي. تختبر صحةRealtime عدم إعادة هدم اتصال تعافى، واستقلال مستمع الرسائل دون الدفتر. اختبارات التشخيص تمنع حفظ نصوص الاستثناءات أو معرفات الحسابات أو الرموز السرية.

اختبارات الرسائل عبر HTTP الفعلي تتحقق من أن التسجيل المؤكد من المزامنة يجعل رسالتين متتاليتين تحتاجان طلبRPC واحدًا لكل منهما، وأن فشل التسجيل لا ينشئ تأكيدًا، وأن اختلاف الحساب يمنع استخدام التسجيل السابق، وأن إلغاء التأكيد أو مرور60 ثانية يعيد فحص الحساب وتسجيل الجهاز. التأكيد مؤقت في الذاكرة ولا يستعاد من نسخة احتياطية.

تظل اختبارات Room/Compose وFCM ونسخ السحابة وlintRelease وبناءAPK وتوقيع الإنتاج ومقارنته بالإصدار السابق مطلوبة. لا تغيير لصلاحيات RLS أو مخطط الخادم أو كلمات المرور أو الديون أو التسديدات أو أرشيف العمليات أو الحزمة أو مفتاح التوقيع. لا عودة لمساعد واتساب أو Termux؛ أزيل استثناء localhost القديم من سياسة الشبكة.

## التشخيص على الهاتف عند استمرار الإخفاق

الدخول والضبط يعرضان «الإصدار المثبت» ويتيحان «فحص الاتصال». الفحص ينفذ GET /auth/v1/health فقط عبر مسار SDK وعبر HTTPS الخاص بأندرويد، دون إرسال بيانات دخول أو أموال. نجاح أحد المسارين وفشل الآخر يحدد أن المشكلة داخل مسار العميل، وفشلهما برمزDNS/TLS يحدد مرحلة الاتصال. نجاح health وحده لا يثبت صحة كلمة المرور أو الصلاحيات أو المزامنة.

«نسخ تفاصيل الفحص» ينسخ الإصدار وAndroid ورمز الإخفاق ومساره العام ووقته ونتيجة الفحص فقط. لا كلمات مرور ولاaccess/refresh tokens ولا أسماء أو مبالغ أو أرقام هواتف. النسخ يتم بضغط المستخدم، ولا يُرسل التقرير تلقائيًا إلى أي شخص.

بوابة الإغلاق الميداني: تثبيت فوق النسخة الحالية، التأكد من رقم الإصدار المثبت، نجاح الدخول، نزول الطابور إلى صفر، تحقق عملية واحدة مسجلة أصلًا في الهاتف الثاني، ثم التحقق من تنبيه/رسالة يرسلها المستخدم بنفسه. لا تحذف التطبيق ولا تكرر مبلغًا محفوظًا ولا ترجع إصدارًا أقدم فوق قاعدة البيانات. لا يُعلن أن جميع أخطاء أجهزة المستخدم انتهت قبل هذا التحقق أو تقرير فحص من الهاتف المتعطل.
