# الاسترداد الآمن — 3.3.22.21 (89)

## المشكلة والسبب في المصدر

المسار السابق كان يسجل منتقي الملفات داخل شاشة Compose شرطية، ويحتفظ بالنسخة المقروءة ومعاينتها في remember فقط. يفقد ذلك العمل عند خروج الشاشة من التركيب أو إعادة إنشاء النشاط/العملية، ولا توجد نسخة مرحلية دائمة للملف أو جلسة يمكن استئنافها. يبدأ التطبيق بجذور تحميل/قفل/تنقل مستقلة؛ الاعتماد على بقاء شاشة الإعدادات حية أثناء DocumentsUI لا يضمن رجوع النتيجة إليها. لا يوجد سجل استثناء من هاتف المستخدم يثبت استثناء بعينه؛ يغطي اختبار الانحدار إعادة إنشاء النشاط وفقد المتحكم أثناء منتقي الملفات.

علاوة على مشكلة الواجهة، كانت الاستعادة تستبدل جميع الصفوف محليًا، وتمسح صندوق الرفع وتضع restore_hold. وكانت المصالحة اللاحقة تختار بيانات الخادم. لذلك لم يكن المسار السابق مناسبًا لدمج عمليات جهاز قديم ورفع الناقص بأمان.

## المسار الجديد

- نشاط داخلي غير مُصدّر للاسترداد؛ تسجيل OpenDocument دائم خارج تركيب شاشة الدخول أو التنقل. يبقى اختيار الملف والمعاينة والتقدم في واجهة الاسترداد.
- يُنسخ URI إلى ملف خاص بالتطبيق ببث محدود، ثم fsync وتثبيت الملف. تُحفظ إحالة المصدر أثناء النسخ، وتُستأنف عند العودة. بعد اكتمال النسخ لا يلزم بقاء مزود الملفات أو إذنه متاحًا. لا يُعاد استخدام ملف سابق عند فشل اختيار جديد.
- فحص تنسيق الملف، البصمة، العلاقات، المبالغ، المعرّفات المكررة، وتسلسل الديون والتحصيل قبل التعديل. تطبق حدود الحجم والذاكرة برسالة واضحة.
- مقارنة أعداد الزبائن، الديون مع الرصيد الافتتاحي، التسديدات، الرصيد المتبقي، وعدد عمليات كل نوع. تُحسب الإضافات والمطابقات والتعارضات من الصفوف الفعلية ومعرّفاتها.
- زر «تأكيد استرداد البيانات»: نسخة حماية محلية مشفرة ومقروءة للتحقق أولًا، ثم معاملة Room واحدة تضم إضافات السجلات وحمايتها وطلبات التحقق الدائمة ونتيجة الجلسة. لا حذف للبيانات الحالية ولا مسح للصندوق المالي المعتاد.
- يُعاد فحص رقم تسلسل البيانات عند التأكيد؛ تغيرها أثناء المعاينة يستدعي مقارنة جديدة. إخفاق النسخ أو المعاملة يترك البيانات الأصلية، ونجاح المعاملة ثم انقطاع التطبيق يُستأنف من الجداول الدائمة.

## سياسة التعارض والمزامنة

| الحالة | التصرف |
| --- | --- |
| المعرّف موجود محليًا والبيانات متطابقة | لا تكرار؛ يُتحقق من وجوده الفعلي على الخادم |
| المعرّف موجود بقيم مختلفة | الاحتفاظ بالمحلي الحالي وعرض التعارض؛ لا استبدال تلقائي |
| معرّف آخر مع حركة مماثلة في المبلغ/النوع/الزبون/التاريخ/التفاصيل | تعارض للمراجعة، لا افتراض أنها حركة جديدة |
| معرّف قديم لا يصلح لهوية UUID السحابية | عرض للمراجعة؛ لا إنشاء معرّف بديل ولا رفع تخميني |
| مفقود محليًا وواضح الهوية | إضافة مع المعرّف الأصلي وربط الزبون الأصلي وحماية من الجلب السحابي أثناء التحقق |
| موجود على الخادم ومتطابق | إقرار التحقق دون POST للحركة |
| مختلف أو محذوف على الخادم | إبقاء التعارض وحماية النسخة المحلية؛ لا إحياء محذوف تلقائيًا |
| مفقود على الخادم بعد مراجعة الهويات والعلاقات | INSERT فقط، ثم قراءة السجل للتحقق؛ لا UPSERT في مسار الاسترداد |
| رد الحفظ مفقود أو الإنترنت منقطع | الطلب يبقى معلقًا؛ المحاولة التالية تقرأ الخادم قبل أي إدراج آخر |

تُربط الطلبات بمعرّف الحساب والصيدلية عند تأكيد الاسترداد. لا ترسل إلى حساب أو صيدلية مختلفة. المعالجة مستقلة عن الطابور المالي المعتاد؛ توجد حماية محدودة للسجلات المستردة فقط تمنع تعديلها أو حذفها أثناء تحققها، وتحميها من snapshot/bootstrap المعتاد. تُرفع حماية السجل بعد التحقق الفعلي فقط. لا تُوثق المزامنة من علامة قديمة داخل الملف.

تظهر حالات التحقق والمؤكد والمتعثر والمتعارض في شاشة الاسترداد. التعارضات لا تُحل باستبدال مالي تلقائي؛ تبقى للمراجعة مع المعرّف والقيمة والسبب. توجد إعادة محاولة للطلبات المعلقة، وجدولة WorkManager عند توفر الشبكة واستئناف عند بدء التطبيق.

## التوافق والحدود

يدعم قارئ النسخ الموجود: .raadbackup المحمول ذو بصمة SHA-256، نسخ JSON الحالية والقديمة raad-pharmacy-backup وabosmra-backup وJSON بلا وسم معروف إذا احتوى الأقسام المطلوبة، والنسخ المحلية المشفرة .rpb مع مفتاح الاسترداد الصحيح. لا يُقبل مقطع تغييرات منفرد كنسخة كاملة؛ يستطيع مسار المجلد القديم جمع السلسلة ثم فتح مقارنة الدمج الجديدة. التشفير الخاص بتثبيت سابق يحتاج مفتاحه؛ لا يمكن اختراعه. النسخ الحديثة المحمولة لا تحتاج مفتاحًا.

الحد الأعلى للملف 128 ميغابايت مع حد معالجة أقل حسب ذاكرة الهاتف. الملف غير المكتمل أو الأحدث بتنسيق غير مدعوم يظهر رسالة ولا يغيّر الدفتر. العمليات غير الموجودة داخل الملف لا يمكن استردادها. لا يُفسر فرق 9 ملايين و5 ملايين كعملية بمبلغ4 ملايين: الاختبار يعيد دينًا5 ملايين وتسديدًا1 مليون، ويفحص الصفوف لا الفرق الإجمالي.

لا تغيير لمخطط Room أو Supabase أو صلاحياته، ولا تسجيل الدخول أو الصفحة الرئيسية أو التنبيهات أو الرسائل أو تقرير PDF/تيليجرام. يستعمل التحديث backup_control الموجودة لتخزين حالة الاسترداد، ويحافظ على سجلات outbox المالية ومراجعاتها.

## التحقق

تشمل الاختبارات: فرق5→9 ملايين من دين وتسديد، التكرار، فقد الرد بعد الحفظ، اختلاف القيم/الحذف على الخادم، الهويات المتشابهة المختلفة، انقطاع الشبكة، فشل نسخة الحماية، فشل المعاملة، تقادم المعاينة، النسخ القديمة، فساد البصمة والملفات غير الصالحة والكبيرة، إعادة إنشاء النشاط أثناء نتيجة منتقي الملفات، فقد العملية ومزود الملف، وحماية مراجعات الطابور المعتاد. يوجد اختبار HTTP بمحرك Supabase/CIO الفعلي ضد localhost مستقل مع التأكد من INSERT وقراءة الإقرار وعدم إعادة POST بعد فقد الرد.

لا تُستخدم بيانات الصيدلية الإنتاجية في اختبارات الكتابة. لا يوجد ملف النسخة الواقعي للمستخدم ضمن هذه المهمة، لذلك نجاح الاختبارات المعزولة لا يثبت أن عملياته الناقصة موجودة داخل ملف بعينه. ولا تعادل محاكاة إعادة الإنشاء وفتح قاعدة البيانات اختبار فصل كهرباء فعليًا على هاتف.
