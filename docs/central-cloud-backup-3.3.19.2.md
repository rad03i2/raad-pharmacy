# النسخ الاحتياطي المركزي — 3.3.19.2

هذا تنفيذ على فرع تطوير مستقل، للإصدار `3.3.19.2` ورقم البناء `57`. لم يُدمج إلى main، ولم تُطبّق ملفات الإعداد على Supabase الإنتاجي، ولم يُنشر APK رسمي لهذا الإصدار. الوظائف المحلية والمزامنة والإشعارات باقية.

**حالة التشغيل الحقيقية عند إعداد هذا التسليم: غير مهيأ. لا يوجد حساب Google مفوض لهذا التكامل، ولا نسخة سحابية حقيقية مسجلة، ولا اختبار استعادة لبيانات الإنتاج.** اجتياز اختبارات البيانات المصطنعة لا يغير هذه الحالة. لا تُفعّل الجدولة أو زر المسؤول قبل إتمام التفويض واختبار الاستعادة أدناه.

## ما تم تنفيذه

- عملية خادمية مستقلة عن الهواتف: PostgreSQL 17، لقطة MVCC مشتركة مع pg_dump، تشمل public/auth/storage/raad_private/extensions. مصدر Supabase الحالي يستخدم PostgreSQL 17. الكتابة المالية لا تُوقَف؛ يجري رفض تغير ملفات Storage أثناء تنزيل محتوى لقطة النسخ.
- تُنسخ البايتات الفعلية للصور والملفات، مع الأسماء والإصدارات وخصائص المجلدات، وليس جدول storage.objects فقط. التحميل محدود الحجم وتحت تحقق الإصدار قبل وبعد وبعد اكتمال الملفات. الملفات الجديدة بعد اللقطة لا تدخل فيها.
- تُحسب أعداد الزبائن والحركات والحسابات والسجلات والأرصدة والعلاقات والعمليات المكررة داخل اللقطة. تُحفظ هذه البيانات داخل manifest مشفر فقط. لا تُكتب في سجلات GitHub.
- ملفات `database.dump.age` و`storage-backup.tar.age` و`manifest.json.age`، باستخدام Age ومفتاح عام للخادم. مفتاح فك التشفير مستقل لدى المسؤول. المجلدات مؤرخة وتحت `Raad Pharmacy - Cloud Backups` الذي ينشئه تطبيق OAuth نفسه؛ لا توجد مشاركة عامة.
- رفع قابل للاستئناف، تجديد Access Token، إخفاق واضح للتفويض الملغى أو امتلاء Drive، SHA-256 بعد إعادة تنزيل كامل كل ملف. علامة اكتمال المجلد ثم تسجيل الحالة. لا تُعرض النسخة غير المكتملة كنقطة استعادة.
- أقفال PostgreSQL وGitHub تمنع تداخل النسخ. إعادة نفس run/request تتحقق من الملفات القائمة ولا تنشئ نسخة مكررة. إعادة run جديد تنشئ نقطة جديدة.
- الاحتفاظ باتحاد آخر 8 نقاط + أحدث نقطة لكل 30 يومًا مميزًا + أحدث نقطة لكل 12 شهرًا مميزًا، بتوقيت العراق. يُفحص آخر ملف جديد قبل نقل الأقدم لسلة Drive. **سلة Drive قد تستمر في استهلاك المساحة حتى تفريغها؛ لا تفرغها إلا بعد مراجعة النسخ المطلوبة.** الملفات المتروكة من تشغيل فاشل بمعرّف مختلف لا تُحذف تلقائيًا، وتحتاج مراجعة المسؤول عند نقص المساحة.
- cron عند UTC `00/06/12/18`، المقابل للعراق `03/09/15/21`. فاحص كل ساعة ينبه بفشل workflow إذا مرّت 9 ساعات أو تجاوز استخدام الحساب 80%. الحالة داخل التطبيق تعرض التحذير أيضًا. يجب أن يفعّل المسؤول إشعارات فشل GitHub Actions على حسابه؛ لم تُضبط قناة بريد/رسائل خارجية.
- واجهة RTL/Cairo وأرقام إنجليزية: حالة الخدمة، آخر محاولة، آخر نقطة متحقق من ملفاتها، موعد متوقع، العدد والحجم والمساحة. أعضاء الصيدلية يقرؤون الحالة، وقائمة مسؤولين منفصلة يمنحها الخادم تتحكم بالسجل/الطلب اليدوي. لا تُستنتج الصلاحية من هاتف أو user_metadata. لا أزرار تنزيل/استعادة وهمية في التطبيق.

## تفويض الحساب المركزي عبر الآلية الرسمية

ينفذ هذه الخطوات المسؤول على حاسوبه. لا يرسل كلمات المرور أو الرموز أو المفتاح الخاص في المحادثة. يختار حساب الصيدلية، ويمكن أن يكون Gmail عاديًا.

1. في [Google Cloud Console](https://console.cloud.google.com/)، اختر/أنشئ مشروعًا مخصصًا للصيدلية، فعّل Google Drive API، واضبط Google Auth Platform: اسم التطبيق، بريد الدعم والتواصل، الجمهور External لحساب Gmail، والنطاق الوحيد `https://www.googleapis.com/auth/drive.file`.
2. انقل حالة النشر إلى **In production** قبل التفويض طويل الأجل. وضع Testing الخارجي مع نطاق Drive يُصدر Refresh Token بمدة 7 أيام وفق [وثائق Google](https://developers.google.com/identity/protocols/oauth2#expiration). حالة Production لا تمنع الإلغاء/انتهاء التفويض لأسباب أخرى؛ النظام يفشل بوضوح ويحتاج إعادة تفويض المسؤول عند ذلك.
3. أنشئ OAuth Client من نوع **Desktop app** لأداة الإعداد المحلية، ونزّل JSON إلى مجلد خاص خارج المستودع. أداة الإعداد تستخدم PKCE وحالة OAuth وcallback محليًا عبر مكتبة Google الرسمية؛ حساب Google لا يُسجل داخل Android.
4. جهز Python 3.12 وAge وPostgreSQL client 17 على حاسوب المسؤول. من المستودع نفذ تثبيت `tools/cloud_backup/requirements.txt`، ثم:

```bash
umask 077
python -m tools.cloud_backup.setup_google --client /secure/raad/oauth-client.json --output /secure/raad/oauth-credentials.json
age-keygen -o /secure/raad/recovery.agekey
age-keygen -y /secure/raad/recovery.agekey > /secure/raad/public-recipient.txt
```

تفتح أداة OAuth صفحة Google الرسمية لاختيار الحساب والموافقة. ملف credentials محمي ولا تُطبع قيمه. يُحفظ recovery.agekey في نسختين محميتين منفصلتين (مثل وسيط غير متصل وخزنة كلمات مرور مشفرة). **لا يرفع مفتاح الاستعادة إلى GitHub أو Google Drive نفسه، ولا يدخل APK أو Secrets. فقدانه يمنع فك النسخ.** اختبر النسختين قبل الاعتماد عليهما.

نطاق drive.file يدير الملفات التي ينشئها **هذا OAuth client**. لا تنشئ مجلد النسخ عبر تطبيق آخر وتتوقع أن يراه التكامل. الحساب يملك البيانات؛ التطبيق لا يمنح المستخدمين الآخرين روابط Google أو تفويضًا.

## إعداد التشغيل بعد موافقة المالك

هناك ثلاث خطوات منفصلة للموافقة: نشر جداول التحكم/Edge، تفعيل النسخ، ثم دمج التطبيق/نشر الإصدار. لم تُنفذ أي منها أثناء التطوير.

1. راجع وطبق `supabase/cloud-backup-control.sql` فقط. الملف إضافي ومتكرر التطبيق، ولا يغير صفوف العملاء والحركات أو حسابات Auth. امنح المستخدم المخول بصف واحد في cloud_backup_admins بعد التحقق من ملفه وpharmacy_id. لا تمنح authenticated حق كتابة هذه القائمة.
2. أنشئ GitHub Environment باسم `cloud-backup`. اسمح لفرع main فقط، واحمِ تحديثاته، ولا تضف موافقة بشرية **لكل تشغيل مجدول** إذا أردت التشغيل دون تدخل. لا يُستخدم pull_request_target لقراءة الأسرار.
3. خزن الأسرار التالية فيه عبر الواجهة أو أداة gh المحلية: `CLOUD_BACKUP_DB_URL` (Direct أو Session pooler؛ ليست transaction pooler/6543)، `CLOUD_SUPABASE_SERVICE_ROLE_KEY`، `CLOUD_GOOGLE_CLIENT_ID`، `CLOUD_GOOGLE_CLIENT_SECRET`، `CLOUD_GOOGLE_REFRESH_TOKEN`، `CLOUD_AGE_RECIPIENT` (عام فقط).
4. تجنب كلمات المرور في argv/history. أداة `install_secrets.py` تقرأ ملفي credentials وserver-config خاصين خارج المستودع؛ الثاني يحتوي `database_url` و`service_role_key` و`age_recipient`. بعد `gh auth login` للمسؤول، ترسل القيم عبر stdin دون طباعة:

```bash
python -m tools.cloud_backup.install_secrets --credentials /secure/raad/oauth-credentials.json --server-config /secure/raad/server-config.json
```

5. بيانات قاعدة النسخ تحتاج قراءة جميع المخططات المعنية وتصدير snapshot، مع كتابة **جداول التحكم الأربعة فقط**. مخططات Auth/Storage تحت صلاحيات Supabase المدارة قد تتطلب postgres المالك. استخدم حسابًا مخصصًا وقلص منح الكتابة قدر الإمكان؛ أي كلمة مرور إدارية متاحة للrunner لها أثر أمني ويجب حمايتها/تدويرها. ربط PostgreSQL يفرض TLS verify-full ويقيد مرجع المشروع. أسرار Vault نفسها لا تُصدّر. JWT/إعدادات SMTP ومقدمي الدخول خارج النسخ وتحتاج حفظًا إداريًا منفصلًا.
6. أول اختبار يمكن تشغيله محليًا في بيئة المسؤول بنفس متغيرات الخادم و`GITHUB_RUN_ID` معرف اختبار فريد؛ لا يحتوي الكود قيمًا حقيقية. يشغل `python -m tools.cloud_backup.runner` بعد إعداد جداول التحكم. ثم ينفذ الاستعادة المعزولة قبل السماح بالجدولة.
7. بعد الموافقة على الدمج، اضبط Repository variable `CLOUD_BACKUP_ENABLED=true`. الجدولة تعمل على default branch فقط. GitHub قد يؤخر التشغيل، وقد يعطل الجداول في مستودع عام غير نشط؛ راقب GitHub والحالة، ولا تعتبر cron ضمانًا للتوقيت أو حماية من فشل GitHub نفسه. إذا كانت متطلبات الاستمرارية أشد، انقل نفس المحرك إلى scheduler/worker دائم مع مراقبة مستقلة.
8. انشر Edge Function `cloud-backup` بمصادقة JWT وفحص getUser داخلها؛ API يحتاج SUPABASE_URL/ANON_KEY/SERVICE_ROLE_KEY من بيئة الخادم. ضع `CLOUD_BACKUP_AUTOMATIC_ENABLED=true` فقط بعد تشغيل الجدولة فعليًا. للطلب من التطبيق، خزّن PAT محدودًا بـActions write لهذا المستودع فقط في `CLOUD_BACKUP_DISPATCH_TOKEN` داخل أسرار Edge، وفعل `CLOUD_BACKUP_MANUAL_ENABLED=true` بعد نجاح الاختبار. المستودع والworkflow والفرع main ثابتة على الخادم. JWT والصيدلية وقائمة المسؤولين تُفحص من الخادم/RLS لكل طلب.

مستخدم التطبيق لا يحتاج تسجيل Google أو مفتاحًا إداريًا. مفتاح Supabase publishable الحالي ليس سر خادم، ولا يُضاف أي secret جديد إلى BuildConfig.

## الاستعادة المعزولة وإثبات النجاح الحقيقي

الأداة تقبل **localhost فقط**؛ لا يوجد خيار لاستعادة الإنتاج أو تجاوز القيد. يتم تنزيل الملفات المشفرة إلى مجلد خاص خارج checkout، وتُفك داخل مجلد مؤقت يُحذف حتى عند الفشل. يمنع استخراج الروابط ومسارات traversal، ويتحقق من بصمات الصور، وأعداد العملاء والحركات والحسابات وأرصدة مالية وعلاقات وعدم تكرار operation_id.

1. المسؤول الموثق في Google يختار مجلدًا مكتملاً من الحساب الصحيح، ويستخدم مفتاح الاستعادة الخارجي. هوية التطبيق لا تمنح بقية المستخدمين الوصول إلى Drive. أداة المكتب مستقلة عن زر التطبيق وتحتاج حساب المالك/التفويض والمفتاح معًا.
2. جهز PostgreSQL 17 جديدًا محليًا بلا جداول في المخططات المعنية، وأدوار وإضافات Supabase المطابقة لإصدار المصدر. لا تستخدم بيانات حقيقية في CI العام. pg_dump يحفظ مراجع الأدوار والإضافات والسياسات؛ لا ينشئ جميع أدوار منصة Supabase وخدماتها، وقد يفشل في بيئة vanilla أو إصدار Auth مختلف. يُوقف الاختبار عند أي خطأ، ولا يتجاهل أخطاء الاستعادة.
3. احفظ DSN المحلي في متغير `ISOLATED_RESTORE_DB_URL` عبر مدير الأسرار. لا تمرره على سطر الأوامر. ثم:

```bash
python -m tools.cloud_backup.restore --credentials /secure/raad/oauth-credentials.json --identity /secure/raad/recovery.agekey --folder DRIVE_BACKUP_FOLDER_ID --output /secure/raad/rehearsal-encrypted --restore-local --storage-local-url http://127.0.0.1:54321
```

`--storage-local-url` اختياري لكنه **مطلوب لإثبات استعادة Storage API كاملة**؛ يحتاج خدمة Supabase Storage محلية بمفتاح مستقل في `ISOLATED_STORAGE_SERVICE_ROLE_KEY`. ترفع الأداة البايتات بأسماءها الأصلية ثم تعيد تنزيلها وفحص SHA-256. يمكن فحص الملفات فقط بحذف restore-local/storage-local-url؛ هذا لا يثبت استيراد قاعدة البيانات.

4. راجع SQL functions/roles/extensions الخاصة بالمنصة. بعض وظائف قاعدة البيانات والمراجع الخارجية لا تدخل في schemas المختارة (مثل pg_net وcron وVault). احتفظ بتكوين المنصة الآمن والEdge Functions وFCM ومزودي Auth وSMTP/JWT من مصادرها الإدارية، ولا تدع إعادة إنشائها تنفذ إشعارات أثناء الاختبار. البيئة المحلية معزولة عن الشبكة الخارجية والأجهزة وFCM قبل الاستيراد.
5. Auth: محفوظة جداول المستخدمين والهوية وpassword hashes وملفات الصلاحيات. جلسات الدخول/refresh_tokens/تحديات الدخول المؤقتة تُستثنى؛ يحتاج المستخدمون تسجيل الدخول مجددًا. استعادة hashes في fixture لا تثبت تسجيل دخول خدمة Auth الفعلية. اختبر كلمة مرور حساب اختبار مع GoTrue مطابق، سياسات المستخدمين ومقدمي OAuth والإعدادات؛ لا تغير كلمات المرور على الإنتاج.
6. وثق معرف النسخة وتاريخها ونجاح DB/Storage/Auth واختبار تسجيل الدخول في تقرير خاص، ثم حدّث `cloud_backup_status.restore_tested_at` إداريًا فقط بعد نجاح تلك الاختبارات. لا يملؤه runner أو CI تلقائيًا. في هذه النسخة لا يوجد تحقق آلي لتسجيل دخول GoTrue؛ هذا يبقى ضمن اعتماد المسؤول للبيئة المطابقة.

### خطة استعادة الإنتاج لاحقًا — ليست منفذة في الأداة

موافقة صريحة من المالك، تحقق حديث من هوية المسؤول، نسخة أمان حديثة من الحالة الحالية، مقارنة العمليات بعد تاريخ النقطة المرشحة وتحديد ما سيُفقد/يُرحل، إيقاف الكتابة ومزامنة **كل الأجهزة**، مراجعة العمليات المعلقة والمحذوفة وoperation_id. لا تعيد توصيل الأجهزة بقاعدة قديمة فورًا. استخدم خطة قطع/تهيئة قواعد الهواتف وإبطال الجلسات وإعادة جلب الحالة المركزية مع المصالحة قبل السماح بالكتابة. راجع آثار Restoring Auth/Storage وRealtime والإشعارات. أي استعادة إنتاج تحتاج مراجعة منفصلة وموافقة؛ الأداة الحالية ترفضها.

## حالات الفشل وحدود التشغيل

Supabase متعطل: تشغيل فاشل/تنبيه ثابت بلا بيانات حساسة، ولا تُرفع نقطة ناقصة ولا تُحذف آخر نقطة سليمة. انقطاع Google: retries بتأخير وحد أقصى، رفع resumed بحسب Range الذي يؤكده الخادم، والجلسة المنتهية يعاد بدء رفعها بنفس file ID. إلغاء Refresh Token: يلزم إعادة OAuth الرسمية. تحرك صورة وقت النسخ: يفشل تشغيلها حفاظًا على الاتساق، ويعاد التشغيل التالي/يدويًا. ليست هناك retry غير محدودة أو ادعاء بمحتوى لم يصل للسحابة.

المساحة من Drive about تشمل حساب Google كله وسلة المحذوفات. عدد النقاط قد يبلغ بحد أقصى 50 مع تداخل كبير بينها؛ الحجم يعتمد على DB والصور. ملفات Storage الفردية الحالية محدودة 5MiB، وأداة النسخ ترفض >100MiB دون مراجعة. عمليات النسخ تستهلك تنزيل Storage/DB ورفع/تنزيل Drive والتحقق؛ ضع في الحسبان حدود API ومعدل الطلبات وخطة Supabase وخطة GitHub والحساب. لا توجد تكلفة خدمة ثالثة ثابتة أضيفت هنا، وقد تحتاج مساحة Google مدفوعة أو دقائق تشغيل حسب خطتك. لا تُضمن تغطية التغييرات المحلية التي لم تصل للسحابة.

## ما يمكن وما لا يمكن إثباته قبل التفويض

اختبارات CI تعمل على بيانات مصطنعة: PostgreSQL 17 الحقيقي، Age حقيقي، استيراد قاعدة جديدة، hashes حسابات اختبار، استثناء جلسات الدخول، صور وبصمات حقيقية، RLS لمسؤول/مستخدم/صيدلية ثانية، مع Google/Storage transport محاكى. اختبارات التطبيق تشمل الحالة غير المهيأة والتحذير والصلاحية وأرقام/وقت العراق، إضافة إلى اختبارات المشروع السابقة.

**يبقى معطلًا خارجيًا:** تفويض حساب الصيدلية، أسرار الاتصال، أول نسخة حقيقية، تنزيلها وفكها بمفتاح المسؤول، استعادة Supabase/Auth/Storage المطابقة وتوثيقها، نشر Edge وجداول التحكم، تفعيل الجدولة والرسائل التشغيلية، ثم الموافقة على الدمج/الإصدار. إلى ذلك الحين لا توجد إجابة عن بريد الحساب المالك أو موعد آخر نسخة ناجحة، وتعرض الواجهة ذلك بوضوح.

المراجع الرسمية: [Drive scopes](https://developers.google.com/workspace/drive/api/guides/api-specific-auth)، [OAuth desktop](https://developers.google.com/identity/protocols/oauth2/native-app)، [resumable uploads](https://developers.google.com/workspace/drive/api/guides/manage-uploads)، [PostgreSQL 17 pg_dump](https://www.postgresql.org/docs/17/app-pgdump.html)، [Supabase restore](https://supabase.com/docs/guides/self-hosting/restore-from-platform)، [Age](https://github.com/FiloSottile/age)، [GitHub schedules](https://docs.github.com/en/actions/reference/workflows-and-actions/events-that-trigger-workflows#schedule).
